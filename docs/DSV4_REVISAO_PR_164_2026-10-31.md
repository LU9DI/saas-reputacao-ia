## Ponto 1 — O sitemap estático pode ser publicado e servido com `filtra-indice` suspenso?

**Resposta curta: o artefato pode ser gerado e hospedado hoje, mas NÃO fica
acessível nas URLs declaradas sem uma decisão de rota.** O arquivo existe; a rota
não existe.

### Evidência (medida agora)

| Requisição | Resultado | Leitura |
|---|---|---|
| `GET /indice/sitemap/0.xml` | `200` · `x-indice-proxy: render-stale-cache` | vem do cache do Worker, não da origem |
| `GET /indice/sitemap/1.xml` | `429` | sem cópia em cache naquele PoP → origem recusada |
| `GET /indice/sitemap/0.xml?probe=1` | **`503`** · `x-indice-upstream-status: 503` | **sonda sem cache: a origem está morta** |
| `GET /indice/sitemap-0.xml` (rota nova) | **`503`** · `x-indice-proxy: render-origin` | o Worker intercepta **todo** `/indice/*` |
| `GET /indice/static/sitemap-0.xml` (rota nova) | **`503`** · `x-indice-proxy: render-origin` | idem |
| `GET /sitemap-indice-0.xml` (raiz) | **`404`** · `cf-cache-status: DYNAMIC` · **sem** `x-indice-proxy` | raiz **não** passa pelo proxy do Índice: chega no frontend |

Código que causa isso — `infra/cloudflare/filtra-indice-proxy.js`:

- `:1` origem fixa `https://filtra-indice.onrender.com`;
- `:92-94` intercepta qualquer caminho `/indice` ou `/indice/...`;
- `:3` `CACHEABLE_PATH = /^\/indice\/(?:sitemap-index\.xml|sitemap\/\d+\.xml)$/`
  — só esses dois padrões são servidos de cache; o resto sempre vai à origem.

### O que isso significa

Publicar `indice/.static-sitemaps/*.xml` em Pages/R2/KV **não** torna
`filtraai.com/indice/sitemap/0.xml` acessível, porque a URL continua sendo
resolvida pelo Worker para o Render suspenso. "Publicar o artefato" não é um passo
autossuficiente.

### Opções reais (ordenadas por risco)

| # | Caminho | O que exige | Risco | Efeito |
|---|---|---|---|---|
| **A** | Ensinar `filtra-indice-proxy` a servir `/indice/sitemap*` de origem estática (mesmo padrão de `filtra-indexnow-key.js`, que já tem `STATIC_SEO_ORIGIN` + validação + cache) | deploy do Worker (Cloudflare) | baixo-médio: mexe no caminho de descoberta; validar XML antes de servir | resolve a descoberta sem Render |
| **B** | Publicar os shards na **raiz do frontend** (`/sitemap-indice-0.xml`, `-1`, `-2`) e apontar o índice central para eles | deploy do frontend (sem tocar em Cloudflare) | baixo: raiz já é servida pelo frontend (provado: o 404 vem do frontend, não do proxy) | resolve a descoberta sem Render **e** sem deploy de Worker; muda a URL dos arquivos (os `<loc>` internos continuam `/indice/...`) |
| **C** | Manter como está e esperar o Render voltar | reativar o serviço (billing) | alto: shards expiram do cache em ≤7 dias | nada a fazer |

**Recomendação:** **B** como correção estrutural (não depende de Cloudflare nem de
Render) e **A** como endurecimento posterior. Mudar a URL dos arquivos de sitemap é
decisão do proprietário, porque altera os 3 sitemaps já conhecidos pelo GSC — os
`<loc>` internos não mudam. Nenhuma das duas foi executada: exigem deploy, fora da
autorização desta tarefa.

## Ponto 2 — Frontend e Cloudflare servem os arquivos corretos, sem conflito de rota ou cache?

**Resposta curta: o roteamento é coerente por desenho, mas existem três armadilhas de
cache/configuração e uma documentação divergente.** Duas foram corrigidas nesta
revisão; as demais ficam documentadas com evidência.

### 2.1 Rotas (sem conflito estrutural, com acoplamento explícito)

- `/indice/*` -> Worker `filtra-indice-proxy` -> app Node do Índice. O frontend **não**
  serve `/indice/*` (confirmado: `filtra-ai-frontend.filtra-ai.workers.dev/indice/sitemap/0.xml` -> 404).
- `/sitemap.xml` e `/robots.txt` -> Worker `filtra-indexnow-key` em rota exata.
- Demais caminhos da raiz -> frontend.
- Consequência de desenho: o **índice central** (`/sitemap-index.xml`, no frontend)
  declara 3 filhos que vivem em **outro** processo. Se o outro processo cai, o índice
  continua anunciando filhos mortos e o GSC reporta "não foi possível buscar" para 3
  de 4 sitemaps. É o estado atual (P0-2 do relatório principal).

### 2.2 Cache do Worker do Índice (armadilha de observabilidade)

`filtra-indice-proxy.js:4-6`: `FRESH_CACHE_MS = 60_000`, `STALE_CACHE_SECONDS = 604800`.

- O caminho *stale* devolve `cache-control: no-store` (`:154-159`): evita que a borda
  cacheie a cópia de contingência, mas ainda a serve.
- **Os cabeçalhos não provam saúde.** Medido: `/indice/sitemap-index.xml` respondeu
  `200` com `x-indice-proxy: render-origin`, `x-indice-cache: refreshed` e
  `x-indice-upstream-status: 200` **enquanto a origem devolvia 503**. Esses campos
  descrevem a cópia em cache, não o estado atual.
- **Sonda confiável:** requisição com query string não é cacheada (`:96-100`) e vai à
  origem -> `?probe=1` devolveu **503** com `x-indice-upstream-status: 503`.
- **Corrigido nesta revisão:** `frontend/scripts/verify-production-seo.mjs` faz essa
  sonda por shard e falha com mensagem explícita quando o 200 é só cache.

### 2.3 Fallback de `robots.txt` no Worker de SEO (divergência corrigida)

`infra/cloudflare/filtra-indexnow-key.js:68-86` gera um `robots.txt` em código quando
* a origem falha. Esse fallback ainda anunciava `Sitemap: https://filtraai.com/sitemap.xml`,
  ou seja: a correção do `robots.ts` seria **desfeita** justamente no cenário de falha.
- Corrigido: o fallback anuncia apenas o índice central e o índice do Índice.
- Guardrail novo: `infra/cloudflare/filtra-indexnow-key.test.mjs` (5 testes) falha se a
  lista de crawlers ou a lista de sitemaps do Worker divergir de
  `frontend/src/app/robots.ts`.
- Pendente: publicar o Worker (deploy Cloudflare) para o comportamento valer em produção.

### 2.4 Sitemap estático usado como fallback está defasado (risco real, não corrigido)

`filtra-indexnow-key.js:2` -> `STATIC_SEO_ORIGIN = https://filtra-ai-frontend.filtra-ai.workers.dev`.
Esse deployment estático **responde** (`/sitemap.xml` -> 200, 57.804 B; `/robots.txt` -> 200),
mas o conteúdo está velho:

| Métrica | Valor medido no fallback estático |
|---|---|
| URLs | **125** |
| `<lastmod>` | **0** |
| `hreflang="zh"` | **112** |
| `x-default` | **0** |
| contém `/planos` | **não** |

Numa falha da origem principal, o site serviria um sitemap com 112 alternates `zh`
apontando para páginas `noindex`. O `sanitizeStaticSitemap` remove URLs `/zh`, mas os
`<xhtml:link hreflang="zh">` **permanecem** (o sanitizador filtra `<url>` inteiros).
Ação recomendada: republicar o export estático a partir do `main` corrigido e, se
quiser blindar, remover `xhtml:link` com `hreflang="zh"` no sanitizador. Não alterei
o sanitizador para não mudar comportamento sem deploy coordenado; o contrato atual
está documentado e coberto por teste.

### 2.5 Documentação de topologia divergente

`.github/workflows/README.md` diz que `/robots.txt` e `/sitemap.xml` vêm da **Vercel**,
mas `filtra-indexnow-key.js:1` usa
`SEO_ORIGIN = https://filtra-ai-web-runtime.onrender.com`. O comentário de
`frontend/src/app/sitemap-index.xml/route.ts` também citava "Vercel". Isso importa para
saber **onde** publicar: corrigir o sitemap exige deploy do origin que o Worker de fato
lê. Registrado como pendência de documentação (não corrigi o README para não afirmar
topologia sem acesso ao painel).

## Ponto 3 — Permissão de CI: onde está o bloqueio e como resolver sem expor segredo

### 3.1 O que aconteceu (evidência literal)

```
$ git push -u origin cline/zv5xh6c6
 ! [remote rejected] cline/zv5xh6c6 -> cline/zv5xh6c6
   (refusing to allow a GitHub App to create or update workflow
    `.github/workflows/indice-ci.yml` without `workflows` permission)
```

### 3.2 Causa, sem tocar em credencial

- A autenticação deste ambiente é feita por um **GitHub App** installation token
  injetado pela infraestrutura (`gh auth status` -> conta `cline-cloud[bot]`, token
  mascarado). Nenhum segredo foi lido, copiado, armazenado ou impresso.
- O GitHub exige a permissão de app **`workflows`** para criar/atualizar arquivos em
  `.github/workflows/**`. A instalação atual não a concede.
- Não é falta de "token pessoal": é escopo de permissão do App. Contornar com PAT
  seria exatamente o que a instrução proíbe.

### 3.3 O que foi feito em vez de forçar

1. `.github/workflows/indice-ci.yml` foi **revertido** para o estado de `main` na branch
   (nenhum workflow alterado no diff — verificável em `git diff main...HEAD`).
2. O passo de CI ficou **documentado como patch** no relatório principal (§2.1), pronto
   para colar por quem tem a permissão:

   ```yaml
       - name: Sitemap estático (materializa e valida os 3 shards)
         run: |
           npm run sitemaps:static
           npm run sitemaps:static:check

       - name: Worker de SEO (robots/sitemap fallback alinhados)
         run: node --test infra/cloudflare/filtra-indexnow-key.test.mjs
   ```

3. Alternativas legítimas, em ordem de preferência — todas sem manipular secrets:
   **(a)** o proprietário concede `Workflows: read & write` ao App `cline-cloud` e um novo
   push aplica o patch; **(b)** o proprietário aplica o patch em commit próprio ou numa PR
   separada; **(c)** o patch entra num PR aberto por uma conta humana com permissão.
   **Não recomendado:** criar PAT de escopo amplo, desativar proteção de branch ou
   remover o job do CI.
4. Higiene verificada: `git diff main...HEAD` não contém `ghp_`, `github_pat_`,
   `Bearer <...>`, `SECRET`, `TOKEN` ou `password` (contagem = 0). O relatório cita
   apenas nomes de variáveis (`RENDER_API_KEY=unset`, `CLOUDFLARE_API_TOKEN=unset`),
   nunca valores.

### 3.4 Impacto prático

Enquanto o passo não entrar no CI, a validação do artefato estático e do Worker depende
de execução manual. Os dois foram executados nesta revisão: **70/70** testes do Índice e
**5/5** do Worker de SEO.
